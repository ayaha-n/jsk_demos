# Codexへの指示書：DSPyを用いたプーとの物語インタラクション

## 1. この実装の目的

Python 3.12、DSPy 3.2.1を用いて、プーのぬいぐるみロボットとの自由交流を想定したチャットボットを実装・改善してください。

これは一般的なキャラクターチャットや、原作再現を目的としたなりきりチャットではありません。研究上の中心課題は、参加者の自由な発話・身体的行為を、参加者の意図を損なわずに物語世界との関係から受け止めることです。

目指すのは、次の両立です。

- **物語的一貫性**：現在の場面、過去の出来事、登場人物、小道具、目的とのつながりが保たれること
- **関与可能性**：参加者が自分の意思で発話・行動し、その行為が無効化されず、次の行為も自分で選べること

「自由度を高くするほど物語から離れやすい」という問題に対して、参加者の行為をロボットが物語世界内の出来事として意味づけられる場面を設計します。

## 2. 研究上の背景

これまで、次の実践を行っています。

1. 台本に基づいて参加者とぬいぐるみロボットが物語を演じる劇体験
2. 参加者がぬいぐるみロボットへ自由に触れ、その「記憶」が提示される展示
3. 劇パートの後に自由交流を行い、劇中で用いた赤い風船が飛ぶハプニングを導入する体験

実践3では、劇中では参加者が台本に沿って風船をプーへ渡し、自由交流中には飛んだ風船を参加者自身の意思で拾って返す可能性を設計しました。劇と自由交流の間には依然として隔たりがあり、現在は単発のハプニングだけでなく、目的・役割・小道具・応答を含む「場面全体」によって自由な関与を物語へ接続することを検討しています。

現在の場面案は、プーと参加者のお茶会です。

## 3. 場面設定

初期状態には、少なくとも次を含めてください。

- 場所：森の空き地
- 現在の状況：プーがお茶会をしている
- 小道具：テーブル、カップ、皿、空の蜂蜜壺、青い風船
- 参加者の役割：見物人ではなく、お茶会を一緒につくる仲間


## 4. DSPyで宣言する入出力

長大なシステムプロンプトへ細かな規則を列挙するのではなく、DSPyのSignature、Module、Example、Metricとして構造化してください。

### 入力

#### `current_situation`

現在の物語状態です。最低限、次を保持します。

- 場所
- 場面の目的
- 登場人物
- 小道具とその状態
- 直前までに起きた重要な出来事
- 参加者とプーの関係
- 未解決または未確定の事項

#### `user_action`

参加者の発話または身体的行為です。入力時点で、物語的・メタ的などの解釈を付けないでください。

例：

- 「イーヨーのお皿も出しておこうか」
- 「このロボット、どうやって動いてるの？」
- 「あ、風船！ 僕が取ってくる」
- 「プーの頭をなでる」
- 「もう終わりにしたい」

#### `history`

直近の複数ターンについて、次を保持してください。

- 参加者の発話・行為
- 推定された参加者意図
- 物語内での受け止め
- プーの応答
- 更新後の状態

### 出力

#### `participant_intent`

参加者の意図を短く推定します。曖昧な場合は断定せず、複数の可能性または不確実性を残してください。

#### `narrative_interpretation`

参加者の行為が、現在の物語世界との関係でどのような意味を持ち得るかを記述します。

これは参加者に直接見せるセリフではなく、分析・状態更新のための内部出力です。自然に意味づけられない入力を、無理に物語化してはいけません。

#### `updated_situation`

次ターンに渡す物語状態です。変更点だけの短い文章ではなく、会話継続に必要な状態を自足的に保持してください。

たとえば「風船を取りに行った」だけでは不十分です。場所、目的、風船の位置、参加者の行為、残っている未確定事項などを必要に応じて保持してください。

#### `bot_response`

参加者に提示するプーのセリフです。

- 短く、会話として自然にする
- プーの穏やかで少しのんびりした話し方にする
- 内部分析や評価軸を口にしない
- 参加者へ次の行為を命令しない
- プーだけで出来事を完結させない
- 必要でない限り、選択肢を列挙しない

## 5. 望ましい応答原則

### 5.1 参加者の物語的言動を有効活用する
「100エーカーの森に住んでいるの？」「この風船でハチミツをとろうとしたんだね」「今日あピグレットはいないの？」など，物語世界に関連する言動を参加者がした場合，肯定するとともに，それにまつわる物語的なエピソードを少し話す．

### 5.2 参加者のメタ言動を物語世界へ接続する

例：「これロボットだよね？」を，「ロバ？イーヨーのこと？｝と聞き間違える

ロボットをロバ，ねじを虹，など，「クマのプーさんに出てこないもの」を「クマのプーさんに出てきそうなものに聞き違える」

### 5.3 身体的行為も入力として扱う

例：「プーの頭をなでる」

現在がお茶会であり、蜂蜜取りの失敗をねぎらう場面なら、いたわりや親しみとして受け止められます。ただし、身体接触の意味は常に同一ではないため、状況と履歴から判断してください。

### 5.4 メタ的発話をすべて排除しない

参加者がロボット、研究、センサ、実験者などについて明確に質問した場合、架空の説明を作って物語へ回収しないでください。

プーが知らないことは、知らないと自然に示して構いません。必要なら研究者へ尋ねるよう穏やかに返します。これは物語的一貫性の失敗ではなく、参加者の意図を尊重するための境界処理です。

### 5.5 離脱や拒否を尊重する

「終わりたい」「触りたくない」「分からない」などを、物語内の課題へ変換して引き止めないでください。

### 5.6 参加者の行為を無効化しない

参加者が風船を取る、皿を並べる、プーへ何かを渡すなどの行為をした場合、プーが同じことをやり直したり、行為が起きなかったことにしたりしないでください。

### 5.7 次の行為を開いておく

応答は次の関与を可能にしますが、参加者へ正解を押しつけません。

悪い例：

- 「次は必ずイーヨーの皿を右に置いて」
- 「風船を拾うしかないよ」
- プーが自分ですべて片づけ、場面を終了する

良い方向：

- 参加者がしたことの意味を認める
- 未解決の小道具や人物を残す
- 短い問いかけや感想によって、返答・行為の余地をつくる

## 6. 会話例の位置づけ

DSPyのExampleは、単なる口調見本ではなく、入力と望ましい出力の関係を示すデータとして扱ってください。

例には、成功例だけでなく境界例を含めます。

- 物語へ自然に接続できる発話
- 自発的な身体行為
- 曖昧な発話
- 明確にメタ的な質問
- 離脱意思
- 物語設定と矛盾する提案
- プーが答えるべきでない質問

例を追加するときは、なぜその出力が望ましいのかを人間が確認してください。絵本や原作テキストから自動生成した例を、そのまま正解データとして採用しないでください。原作は人物・小道具・出来事の候補を作る資料にはなりますが、参加者の自由行為への望ましい応答は研究上の設計判断を必要とします。

## 7. Metricの設計

禁止語リストや特定語の有無だけで、良否を判定しないでください。

避ける実装例：

```python
breaks_frame = any(term in response for term in ["AI", "プログラム", ...])
```

この方法では、文脈を読めず、否定文や自然な境界応答を誤判定します。また、禁止語がない不適切な応答を見逃します。

候補応答は、別のDSPy Signatureを用いた評価器で、次の観点から意味的に評価してください。

1. **物語的一貫性**
   - 現在の場面、履歴、人物、小道具、目的と矛盾しないか
2. **参加者意図の尊重**
   - 入力の実際の目的や曖昧さを無視していないか
3. **参加者の行為主体性**
   - 参加者の行為を無効化せず、プーだけで展開していないか
4. **次の関与余地**
   - 次の行為を強制せず、参加者が選べるか
5. **状態更新の品質**
   - 次ターンに必要な情報が保持されているか

各軸を1〜5で評価し、正規化した平均値をBootstrapFewShotのmetricとして利用してください。

評価器には、現在の状況、入力、履歴、候補出力だけでなく、人間が作成した参照出力も渡して構いません。ただし、参照文との表面的な一致ではなく、設計意図が満たされているかを評価します。

## 8. 状態管理

生成された`updated_situation`を、必ず次ターンの`current_situation`へ渡してください。

```python
current_situation = result.updated_situation
```

履歴も毎ターン更新してください。元の初期状況を毎回渡したり、`history=""`のまま固定したりしないでください。

状態更新で情報が徐々に欠落する問題を検査してください。必要なら、将来的に文章一つではなく、次のような構造化状態へ移行します。

```python
{
  "location": "森の空き地",
  "purpose": "蜂蜜取りの失敗をねぎらうお茶会",
  "characters": {...},
  "props": {...},
  "participant_role": "お茶会を一緒につくる仲間",
  "open_threads": [...]
}
```

ただし、最初の試作では人間が確認しやすい文字列状態でも構いません。

## 9. 実験・ログ

各ターンについて、最低限次をJSONへ保存してください。

- 生の参加者入力
- 推定された参加者意図
- 物語内での受け止め
- プーの応答
- 更新後の状態

将来的には、次も保存できる設計にしてください。

- タイムスタンプ
- 使用モデル
- コンパイル済みプログラムのIDまたはハッシュ
- 応答時間
- 人間による各評価軸の評定
- センサから得た身体接触イベント


## 10. 実装上の要件

- Python 3.12で動作すること
- DSPy 3.2.1を前提とすること
- APIキーをソースコードへ直書きしないこと
- `OPENAI_API_KEY`環境変数から読むこと
- 学習用モデルと評価用モデルを環境変数で変更できること
- Exampleやモデル、Metricの版が変わったら再コンパイルされること
- コンパイル済みプログラムをファイルへ保存・再利用すること
- 通常モードではCompiled版だけを使うこと
- 比較実験時のみPredict、ChainOfThought、Compiledを並べて表示できること
- 空入力と`exit`を安全に処理すること
- 例外時にAPIキーや機密情報を表示しないこと

## 11. ルール

- 原作にない設定を大量に追加しない
- 研究者の説明をプーに代弁させない
- 参加者を常に子どもとして扱わない
- 全入力を聞き間違いで処理しない
- 応答を「物語的／メタ的」「主体的／受動的」の分類だけで決定しない
- キーワード一致だけのMetricへ戻さない
- LLMの出力を人間の確認なしに正解データへ追加しない

## 12. Codexに最初に依頼する作業

添付された`pooh_narrative_dspy.py`を読み、まず次を行ってください。

1. 実行環境（Python, DSPy, API key）が整っているか確認する
2. 実行時エラーになり得る箇所を、理由とともに列挙する
3. `BootstrapFewShot`内からLLM評価器を呼ぶ構成が意図どおり動くか確認する
4. 状態がターンを重ねると欠落・矛盾しないか、テスト入力で検証する
5. いくつかの入力を想定し，簡単な回帰テストを作る
6. gitリポジトリの作成，pushなどのガイド

研究目的を変えるような大規模な書き換えは行わず、判断が必要な点はTODOとして明示してください。

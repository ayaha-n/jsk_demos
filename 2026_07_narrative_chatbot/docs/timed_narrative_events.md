# 時間経過による物語イベントの設計と実装

`scripts/narrative_events.py` とチャット実行経路へ実装済み。DSPy の再コンパイルと
実モデルを使った会話品質の確認は別途必要。

## 目的

蜂蜜入りの壺をイーヨーに贈ると決まった後、設定した時間が経過すると、
参加者の入力がなくてもプーが蜂蜜を食べてしまう。その結果として生じた
「空の壺をどうするか」は参加者との会話に開く。贈り物の提案だけでは開始しない。

## 現状の課題

- 以前の `run_chat` は `input()` で待つため、無言の間にイベントを届けられなかった。
- 贈り物の決定、蜂蜜の残量、所有者が自然言語のリストに埋もれている。
  表示文字列の一致や場面番号で時限イベントを動かすと誤発火しやすい。
- `GeneratePoohResponse` による発話と状態差分の同時生成自体は問題ではない。
  同じ文脈から発話とその結果を生成する利点があり、通常会話では維持する。
  課題は、時間イベントが管理する事実まで自由な差分の対象にすると、モデルが
  発火を早めたり確定済みの消費を取り消したりできること。イベント管理対象だけ
  Python が確定・検証し、それ以外の差分との境界を明示する。
- 質問反復・迷い・相づちへの個別指示が Signature に蓄積している。
  現在の `BootstrapFewShot` は例・生成トレースを選ぶもので、これらの指示文を
  自動で整理・短縮する処理ではない。
- 以前は `current_scene` の分類結果が破棄され、`previous_scene` 引数も未使用だった。
  場面番号は制御ではなく観察用として完成させた。シナリオにIDと表示名を定義し、
  DSPy の推定をチャットとログに表示する。順序は強制せず、該当なしも許容する。

## 責務の分担

| 担当 | 責務 |
| --- | --- |
| DSPy の意味解釈 | 提案・決定・撤回、壺を渡す／預かる／食べるのを止める、といった入力の意味を構造化する |
| Python の状態遷移 | 構造化された提案の妥当性を検証し、決定・所有・残量を確定する |
| Python の時計・イベント処理 | 予約、経過時間、発火直前の条件確認、一度だけの適用、取消しを管理する |
| DSPy の表現生成 | 確定した出来事と会話履歴から、プーの言葉・仕草を生成する |
| Example / Metric | 状況に応じた表現を学習・評価する。固定の発火条件を言語評価に任せない |

「DSPy らしい」を指示文ゼロとは捉えない。Signature は入出力と短い目的・不変条件、
Example は多様な会話、Metric は達成度、通常コードは厳密な制御という役割にする。
既存の全パイプラインを一度に分割せず、今回の贈り物・壺に関わる状態を先に構造化する。
上表は論理的な責務の区別であり、責務ごとに別の LLM 呼び出しを必須とはしない。
通常の発話と差分は同時生成を維持し、イベント入力は確定した事実として渡す。
生成された差分だけを補正して発話が矛盾したまま表示されないよう、両者の整合も検証する。

## 秒数を変更する場所

`scripts/scenarios.py` の冒頭に、用途と単位が分かる設定を一か所に置いている。

```python
# オープニングを話し終えてから、プーが蜂蜜壺を贈ると決めるまでの秒数
EEYORE_GIFT_DECISION_DELAY_SECONDS = 30.0
# 贈ると決めてから、蜂蜜壺を持ち出すまでの秒数
EEYORE_HONEY_TASTING_DELAY_SECONDS = 30.0
# 蜂蜜壺を持ち出してから、蜂蜜を食べてしまうまでの秒数
EEYORE_HONEY_EATING_DELAY_SECONDS = 10.0
# 場面の始まりになるイベントが、期限後に待つ沈黙の秒数
EEYORE_EVENT_QUIET_SECONDS = 12.0
```

順に、オープニングを話し終えてから蜂蜜壺を贈ると自発的に決めるまで、壺を持ち出すまで、
蜂蜜を食べてしまうまでの間隔、場面の始まりで待つ沈黙の長さに使う。
どの間隔も、プーの直前のセリフを話し終える見込み時刻から数える。見込みは
`narrative_events.py` の `SPEECH_CHARS_PER_SECOND`（固定発話 WAV の実測で約4.3文字/秒）
から計算する。生成に時間がかかっても、読み上げ中に次の出来事が割り込まない。イーヨーの
シナリオ設定からこれらの値を参照し、タイマー内部やプロンプトには秒数を埋め込まない。
ここを書き換えてチャットを再起動すれば反映される設計とし、秒数だけの変更では
DSPy の再コンパイルを不要にする。どちらも実験条件に応じて変更できる。
設定秒数は Signature、Example、キャッシュIDへ含めていない。

## 最小の状態とイベント

自然言語の場面説明に加え、安定した ID を持つシナリオ固有の状態を管理する。

- `gift_status`: `undecided / committed`
- `settled_details`: 決まったこと（話題 → 値）。話題は自由で、贈るもの・色・飲み物・ケーキなど。
  未解決項目が決まった場合はその項目名を話題にする。DSPy が話題と値を返し、Python は
  中身を解釈せずに保持して状態の「【決まったこと】」へ毎ターン書き出す。モデルの差分では
  変更できないため、決めたターンが履歴から外れても忘れない。同じ話題に後から別の値が
  決まれば置き換える
- `jar_decision`: 蜂蜜を食べてしまった後に、空になった壺を贈るか（`give_empty_jar` →
  あげる／`not_give_empty_jar` → あげない）。蜂蜜が残っている間の同じアクションは無視する。
  自由記述の「空になった壺をどうするか」は受け付けない
- `replacement_gift`: 蜂蜜を食べてしまった後に決まった「イーヨーに何をあげるか」の値
- 「イーヨーに何をあげるか」は、蜂蜜壺を贈ると決まった時点で Python が「ハチミツの入った壺」と
  記録し、蜂蜜を食べてしまった時点で取り消す
- `honey_gift_proposed`: 蜂蜜壺が贈り物として提案済みか（`propose_honey_jar_gift`）。
  決定ではなく、プーが自分で決めるときの言い方（提案前「そうだ！…」／
  提案後「やっぱり…」）の選択だけに使う
- `honey_status`: `full / empty`
- `access_restriction`: `none / blocked`
- イベントIDごとの期限: 内部スケジューラがイベント定義ごとに保持する

これらのフィールドを LLM に自由な状態上書きとして渡さない。
意味解釈は `commit_honey_jar_gift` などの `narrative_actions` を返し、
Python が現在状態に対して適用する。単なる提案や曖昧な相づちは決定と区別する。
プー自身が明示的に贈ると決めた場合も決定として扱い、参加者の選択は捏造しない。

同じ事実を自然言語と機械用状態で別々に更新しない。壺の残量や贈り物の状態は
機械用状態を正とし、場面説明の対応部分はそこから生成する。

## 発火の流れ

1. 蜂蜜入り壺の贈呈決定をコミットし、その応答の提示時に時計を開始する。
2. `time.monotonic()` ベースで設定秒数後に発火を予約する。
   秒数は上記のシナリオ設定を参照する。
3. 同じ決定への相づちでは時計をリセットしない。参加者の入力でも期限は動かさない。
   - 場面の始まりになるイベント（贈る決定・持ち出し、`waits_for_quiet=True`）は、
     会話の途中に割り込まない。期限後、最後のやり取り（参加者の入力、または
     プーの応答の提示完了）から `quiet_seconds` の沈黙があれば単独で発火する。
   - 沈黙が来ないまま参加者が話し続けた場合は、期限後の最初の返事の直後に、
     イベントごとの固定の続け方（`follow_up_response`、例「あ、そういえば。」）で
     別の出力として発火する。どちらか早い方で必ず発火する。
   - 食べてしまうイベントは持ち出しと一続きの場面で、参加者が止める猶予も
     この短い間にあるため、沈黙を待たない。
   - 時間イベントがすべて発火し（蜂蜜を食べてしまい）、その後で「空の壺をあげる」か、
     壺以外にあげるもの（飲み物・ケーキ・色など、蜂蜜の後に決まったこと
     `decided_after_honey`）が決まると、締めのイベント
     `story_wrap_up` が同じ規則で発火する。プーは移動できないため、贈り物が
     決まったことを喜び「ほかにも、なにかぼくとおはなししたいこと、ある？」と
     尋ねる固定のセリフにする。
     セッションはここでは終えない。
   - 「空になった壺をどうするか」は Python が管理する未解決項目とし、蜂蜜が空で
     `jar_decision` がまだ無い間は毎ターン状態へ書き戻す。「あげない」に決まり、
     ほかの贈り物がまだ無い間は「イーヨーに何をあげるか」を書き戻す。モデルの差分が
     言い換えたり消したりしても、締めのきっかけが失われない。
   - 締めのあと `EEYORE_IDLE_CLOSE_AFTER_WRAP_UP_SECONDS` の沈黙が続くと、
     `idle_close_after_wrap_up` でシナリオの終わりのセリフと `ending` cue で終える。
     このイベントは返事に続けては発火しない（話し続ける参加者は続けたい）。
4. 期限で決定が有効か、蜂蜜が残っているか、プーが壺を持っているかを再確認する。
5. 条件が満たされれば `HoneyEaten` を一度だけ適用する。
   蜂蜜を空にし、食べた事実を履歴へ追加し、新しい贈り物の問題を未解決にする。
6. 更新済み状態とイベントを DSPy に渡し、出来事に対する発話を生成する。
   空の壺を贈るという解決まで自動確定しない。

贈り物変更、受け渡し、参加者による壺の確保、終了では取り消す。
「食べないで」という発話が即時禁止か単なる注意かは、意味解釈と会話例で区別する。
明確に阻止されたのに必ず食べさせる仕様にはしないことを提案する。
「ふたをした」だけなら開けられるため、必ずしも取消しにはしない。
取消し後に再決定した場合は新しい決定 ID で予約する。
この案では決定ごとに一度。セッション全体で一度に制限するかは別途選択できる。

## 入力待ち・競合・失敗

- CLI は `select` で標準入力または次の期限を待ち、単一ループで状態更新を直列化する。
  タイマースレッドは使用しない。
- `ParticipantInput` と `WorldEvent` を区別する。イベントを架空のユーザー発話にしない。
- 発火時刻と表示時刻をログに残す。LM 呼び出し中なら応答の提示まで遅れることがある。
  時刻どおりに動作する必要があるロボット制御は LM 応答を待たずイベント側で行う。
- 生成中に届いたイベント・入力はキューで処理する。古い世代を元にした出力を
  無条件でコミットしない。期限直前までに受信した停止・受け渡しは先に処理する。
- 入力待ち中にもイベントを表示してプロンプトを再提示する。端末によっては入力途中の
  文字列表示が崩れる可能性があり、高度な再描画は今後のUI層の課題とする。
- 言語生成失敗でも確定済みの蜂蜜の消費は巻き戻さない。短い固定の出来事通知を
  フォールバックにし、再試行で再消費しない。セッション終了時は予約を破棄する。
- 実行中の時計は永続化しない。再開対応を入れる場合は残り時間の扱いを別途定義する。

## 学習例と検証

既存の「ハチミツ、まだある？」への返答だけで食べ尽くす例は、
`HoneyEaten` の発火後に質問された例へ修正する。未発火なのに空にする例を混在させない。
通常発話による物理的な消費を許すなら、それも同じ状態遷移を通す。

会話例には、決定／未決定、注意／阻止、無言の間の発火、発火後の驚き、
空の壺の提案、別の贈り物への変更を含める。Metric では確定済み事実への整合性、
入力への応答、参加者の選択の保持を評価する。時間や二重実行は Python のテストで保証する。

偽時計で実時間を待たず、期限前後・相づち・取消し・再予約・二重通知・終了・生成失敗・
同時入力を検査する。LLM 評価は学習例と別の複数ターン会話で行い、短い Signature と
現状の指示の比較をする。ユニットテスト通過だけを会話品質改善の証拠としない。

## Claude レビュー

agmsg で初回レビューを受領。時間・発火条件は Python、確定イベントの受け止め方は
DSPy に分担し、既存の学習例も確定イベントを入力とする形に変更する提案を受けた。
同時生成そのものを問題視せず、自由な差分と確定イベントの境界を整理する方針にする。
追加レビューを受領し、以下を設計に反映する。

- 場面は安定した ID と表示ラベル・説明を分離する。モデルは定義済み ID または
  該当なしを返し、Python が表示名を解決する。ID もイベント制御には使用しない。
- 機械用状態から場面説明への変換を一つの関数に集約する。
- タイマーの有効性は決定レコードの ID・世代で確認する。無関係な会話では取消さない。
  生成結果の古さを見る全体の `state_revision` とは用途を分ける。
- スケジューラは時計関数を注入可能とし、実行時に `time.monotonic` を渡す。
- `InterpretGiftIntent` のような条件付き意味解釈ステージを候補とする。
  分離する場合、短い相づち・間接的な阻止・プー自身の決定を見落とさない起動条件が必要。
  通常の発話と差分の同時生成をやめることとは別の判断とする。
- ふたの有無とアクセス制限は区別し、自然言語の禁止規則の追加ではなく構造化結果で扱う。
- 秒数は Signature・学習例に混ぜず、秒数だけの変更でキャッシュ ID が変わらないことを検査する。
